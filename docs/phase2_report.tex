\sectiontitle{Project Abstract (2 pts)}
\instruction{(Brief restatement of your project's main goal. Max 300 words).}
\vspace{0.2cm}
\answerbox{Our project looks at a basic problem in banking software: what happens when several requests try to change the same account balance? A withdrawal or transfer may work correctly on its own, but overlapping requests need extra care. We are building a local banking application to demonstrate this using sample accounts and Python threads.
\par\medskip
In Phase II, we have connected the database with deposit, withdrawal and transfer operations. Account locks coordinate the threads, and SQLite transactions keep the debit, credit and transfer record together. If a transfer stops after the debit, rollback restores the balances. The application also checks request keys so that submitting the same request again does not move the money twice.
\par\medskip
The browser interface lets customers view their accounts and carry out transactions. An administrator can review rule alerts for large transfers, rapid activity and repeated failures, plus a separate AI transfer-risk alert. A local prototype was trained on public BankSim data, but its INR calibration remains in progress. An optional interim Groq API review is available when configured, with the local prototype as fallback. The application includes automated tests and examples of lost updates and circular waiting. Our aim is to make thread synchronization and database transactions clear through a working application.}
\gap
\sectiontitle{Updated Project Approach and Architecture (2 pts)}
\instruction{(Describe the current approach, system design, communication protocols and libraries. Max 300 words).}
\vspace{0.2cm}
\answerbox{The current application has two ways to submit banking operations: the Flask pages and the command-line tool. Both call \texttt{transaction\_manager.py}, so the balance checks and transfer logic are shared. Flask 3.1.2 serves the HTML, CSS and JavaScript interface over local HTTP. The lab display receives its updates as JSON.
\par\medskip
\texttt{database.py} prepares the SQLite tables and sample accounts. We store INR 250.50 as 25050 paise; the balance calculations therefore use integers. Separate records hold completed transactions, failed attempts and fraud alerts.
\par\medskip
For a transfer involving accounts 1 and 2, the locking code requests account 1 first, even when account 2 is sending the money. Using the same order for both directions avoids an account-lock cycle. Once the locks are held, \texttt{BEGIN IMMEDIATE} reserves the database writer before balances are read. The debit, credit and history entry are committed together. The failure test interrupts this sequence after the debit to check that rollback restores both balances. Cleanup closes the connection and releases the locks.
\par\medskip
\texttt{client\_sim.py} starts several workers, each using its own connection. This creates competing requests, although SQLite still processes one writer at a time. Password hashes are checked through \texttt{security.py}; the web routes also check account ownership, roles and form tokens. The command-line tool assumes trusted local use. Fraud rules examine activity through the web handlers. A BankSim-trained logistic-regression prototype scores committed transfers using amount, earlier activity and recipient history. When configured, an external Groq API supplies an interim review signal; the local prototype is its fallback. Login failures remain rule-based. The administrator reviews the alerts. Lab demonstrations use temporary data. The next page shows these connections.}

\sectiontitle{Challenges/Roadblocks (7 pts)}
\instruction{(Describe challenges and how you plan to solve them. Max 300 words).}
\vspace{0.18cm}
\answerbox{The main concern is keeping the balance correct when requests overlap. For example, two withdrawals could both read an old balance before either update is saved. The current code uses account locks and a database transaction to protect this sequence. Transfers take the locks in a fixed order so that two threads do not wait on each other's account locks.
\par\medskip
A transfer also needs to recover if it fails halfway through. The tests deliberately stop one after the debit and check that neither account keeps a partial change. The failed attempt is logged after rollback; logging it inside the same transaction would erase the failure record too.
\par\medskip
There is a limit to what the concurrency tests can show about speed. SQLite handles one writer at a time, so more threads can mean more waiting. We still need larger runs to compare timings and check that the balances remain correct.
\par\medskip
The fraud rules also need further checking around their amount and time limits. A legitimate customer may make several transfers quickly, so these cases should be flagged for review rather than treated as confirmed fraud.}
