% PROJECT ABSTRACT
\sectiontitle{Project Abstract (2 pts)}

\vspace{0.05cm}

\instruction{
(Brief restatement of your project's main goal. Max 300 words).
}

\vspace{0.12cm}

\answerbox{3.60cm}{Our project demonstrates how a banking application preserves balances when several requests arrive together. Customers deposit, withdraw and transfer sample funds through a Flask interface. Python account locks coordinate overlapping requests; each money movement uses a SQLite transaction so an interrupted transfer rolls back. Unique request keys prevent retries from moving money twice. A Concurrency Lab shows lost updates, ordered locking and a bounded deadlock example. The administrator reviews rule alerts for high-value or rapid activity and repeated failures. Following mentor feedback to focus on AI implementation, we added an interim Groq review of committed transfers and trained a BankSim-based local prototype. Its calibration for INR transactions and further validation remain in progress. The system is an educational prototype, not a production bank.}

\vspace{0.70cm}

% UPDATED PROJECT APPROACH
\sectiontitle{Updated Project Approach and Architecture (2 pts)}

\vspace{0.05cm}

\instruction{
(Describe your current approach, including system design,
communication protocols, libraries used, etc.\\
Max 300 words).
}

\vspace{0.25cm}

\answerbox{4.75cm}{Flask serves customer and administrator pages over local HTTP. The web interface and command-line tool call the same \texttt{transaction\_manager.py} service. Amounts are stored as integer paise, not floating-point rupees. The service validates an operation, acquires account locks in ascending ID order, opens its own SQLite connection and starts \texttt{BEGIN IMMEDIATE} before reading balances. Debit, credit and the successful transaction record commit together; errors cause rollback. The failed-attempt audit is written separately after rollback. SQLite WAL lets readers overlap with a writer, although SQLite still permits only one writer at a time. The threaded simulator uses separate connections and checks balance invariants. Web routes check password hashes, roles, ownership and form tokens. Rule-based risk scans run after commit. When configured, Groq reviews a committed transfer using amount and recent-activity features; flagged reviews appear in the Risk Desk. The BankSim-trained local model remains a separate prototype and is not used for live scoring. Demo Studio and Concurrency Lab use isolated temporary data.}

% CHALLENGES
\sectiontitle{Challenges/Roadblocks (7 pts)}

\vspace{0.05cm}

\instruction{
(Describe the challenges that you have faced or are facing so far
and how you plan to solve them. Max 300 words).
}

\vspace{0.18cm}

\answerbox{4.05cm}{Overlapping withdrawals can both see an old balance and cause a lost update. Account locks coordinate threads in this process, while \texttt{BEGIN IMMEDIATE} reserves the SQLite writer before balances are read. Opposing transfers might deadlock if each locks its source first; acquiring account IDs in a fixed ascending order prevents that account-lock cycle. A failure after debit must not leave a partial transfer, so the debit, credit and history record share one database transaction and the failure test verifies rollback. Fraud review raises a different challenge: a large but legitimate transfer can be flagged. The current rules and AI response request administrator review rather than automatically reversing a payment. The BankSim prototype still needs INR calibration and evaluation against labelled examples. More threads do not guarantee faster writes because SQLite permits one writer at a time.}
